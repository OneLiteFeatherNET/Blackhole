# Spec Delta

## Purpose
Turns the conversation of every appeal into a complete protocol that is generated by the backend from the stored case events, stored with the case as evidence of kind `TRANSCRIPT`, versioned, and kept consistent with later redactions.

## ADDED Requirements

### Requirement: The protocol is generated from the stored case events
The backend SHALL generate the protocol of an appeal only from the `case_event` rows of that appeal's conversation and its lifecycle markers, never by reading an external system such as Discord, so that the protocol equals the record. It MUST contain every message of the appeal from every channel (`PORTAL`, `PANEL`, `DISCORD`) with visibility `PLAYER` or `STAFF`, in `seq` order.

#### Scenario: Same data, same protocol
- **WHEN** the protocol is generated twice from an unchanged conversation
- **THEN** both outputs are byte-identical apart from the generation time field

#### Scenario: Staff-only message included
- **WHEN** another bot posted a message with visibility `STAFF`
- **THEN** the protocol lists it and marks its visibility

#### Scenario: No external read
- **WHEN** the generator runs in a test with no Discord or network fake present
- **THEN** it completes from the database alone

### Requirement: Protocol content
The protocol SHALL be produced in two renderings of one model: a human-readable text document and a machine-readable JSON document with a `schemaVersion`. Each entry MUST carry sequence number, time, channel, author label and kind, trust, visibility, the full text, every earlier text with its time (edits), the deletion time with the last text kept, attachment metadata and a redaction marker instead of text where redacted.

#### Scenario: Edited and deleted message
- **WHEN** a message was edited once and later deleted
- **THEN** the protocol shows the first text, the edit with its time, and the deletion with the last text kept

#### Scenario: Attachment
- **WHEN** a staff message carried a file
- **THEN** the protocol shows its name, type and size and no URL or bytes

### Requirement: Protocol authors and excluded data
Players MUST be shown under their pseudonymous case label (as on the case timeline, with the opaque participant id in the JSON), staff by display name, unverified staff and other bots with their kind label. The protocol MUST NOT contain a Ban ID, a Discord user id or an owner hash, and internal notes are excluded.

#### Scenario: Author labels
- **WHEN** a player message and a verified staff message are listed
- **THEN** the player appears under the case's pseudonymous label and the staff member under their display name

#### Scenario: No identifiers
- **WHEN** a protocol is captured in a test with a known Ban ID, Discord user id and owner hash
- **THEN** none of them occurs in either rendering

### Requirement: Completeness check in the protocol
The protocol MUST state its completeness check: the number of entries, the first and last `seq`, the digest of the source events, and, for an appeal with a Discord ticket, the ticket's `ticket.transcript_complete` count and last Discord message id. The JSON MUST allow a reader to recompute the entry count and digest.

#### Scenario: Discord ticket
- **WHEN** the protocol of an appeal with a complete Discord ticket is generated
- **THEN** it states the ticket's message count and last message id from `ticket.transcript_complete`

#### Scenario: Portal-only appeal
- **WHEN** the appeal never had a Discord ticket
- **THEN** the check lists the entry count, `seq` range and digest only

### Requirement: When the protocol is created
A protocol SHALL be created when the appeal's conversation closes: on the appeal decision for an appeal without a Discord ticket, and, for an appeal with a Discord ticket, when the ticket closes and its transcript has been verified complete (`ticket.transcript_complete`). A protocol MUST NOT be created for a Discord ticket whose transcript is not verified complete. The protocol is the same for every appeal regardless of the channel the conversation used.

#### Scenario: Decision without Discord
- **WHEN** a moderator decides an appeal that only used the portal and the panel
- **THEN** a protocol version 1 is stored for that appeal

#### Scenario: Discord ticket complete
- **WHEN** a Discord ticket is closed and `ticket.transcript_complete` is recorded
- **THEN** a protocol version 1 is stored in the same request that accepted the completeness proof

#### Scenario: Discord ticket incomplete
- **WHEN** the completeness proof is refused with HTTP 409
- **THEN** no protocol is created

#### Scenario: Generation failure does not fail the decision
- **WHEN** storing the protocol fails after a decision was recorded
- **THEN** the decision stays, the failure is logged without content and the reconciler creates the protocol later

### Requirement: Stored as evidence of kind TRANSCRIPT
The protocol SHALL be stored with the case as an evidence item of kind `TRANSCRIPT` on the appeal's punishment, using the evidence capability's blob storage, audit, access rules and lifetime, and the timeline MUST record `protocol.stored` (appeal id, version, evidence id, entry count, digest; no content). A protocol MUST NOT be stored as a case attachment.

#### Scenario: Stored and recorded
- **WHEN** a protocol is generated
- **THEN** an evidence item of kind `TRANSCRIPT` exists for the punishment and the case has a `protocol.stored` event without content

#### Scenario: Lives as long as the punishment
- **WHEN** the punishment expired years ago
- **THEN** its protocol is still present

### Requirement: Idempotent and versioned
Regenerating the protocol of an appeal SHALL be idempotent: if the digest of the source events equals the latest version's digest, no new version is stored. If the source changed, a new version `n+1` MUST be stored and earlier versions kept as `SUPERSEDED` until a redaction purges them. At most one `ACTIVE` version exists per appeal and concurrent generations MUST NOT produce two versions with the same digest.

#### Scenario: Nothing changed
- **WHEN** generation is requested again for an unchanged conversation
- **THEN** no new version exists and the response names the existing one

#### Scenario: Late edit
- **WHEN** a message is edited after version 1 was stored and the protocol is generated again
- **THEN** version 2 contains the edit, version 1 is `SUPERSEDED` and both are listed

#### Scenario: Concurrent generation
- **WHEN** two generations run at once on the same state
- **THEN** exactly one new version is stored

### Requirement: Late changes are picked up
A reconciler SHALL regenerate the protocol of an appeal whose source digest differs from its active version once the conversation was quiet for `blackhole.protocol.settle-delay` (default PT1M, on the injected clock), and SHALL create a missing protocol for every closed appeal that qualifies. A caller that needs the current state immediately MUST be able to force regeneration without the settle delay.

#### Scenario: Message after close
- **WHEN** a staff message is recorded after the protocol was stored and the settle delay passes
- **THEN** a new version is stored

#### Scenario: Forced
- **WHEN** a forced generation runs inside the settle delay
- **THEN** the new version is stored immediately

#### Scenario: Missing protocol
- **WHEN** a decided appeal has no protocol after a failure
- **THEN** the next reconciler run creates it

### Requirement: Staff access
Staff with role `VIEWER` or above SHALL be able to list the protocol versions of a case, open the human-readable rendering and download the text and JSON from the case page, because they can already read the thread; every open and download MUST be audited as `VIEWED` or `DOWNLOADED`. Downloads MUST be sent as an attachment with `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` and `Cache-Control: private, no-store`.

#### Scenario: Viewer opens
- **WHEN** a viewer opens the latest protocol
- **THEN** the text is shown and a `VIEWED` audit entry is written

#### Scenario: Download
- **WHEN** a moderator downloads the JSON
- **THEN** the response is an attachment with the required headers and a `DOWNLOADED` audit entry exists

#### Scenario: No token
- **WHEN** a request without staff authentication asks for a protocol
- **THEN** the response is HTTP 401

### Requirement: Redaction makes old protocol versions unreadable
When message text or author data is redacted or erased (a message redaction, the erasure of a player's messages, the erasure of a Discord participant, the anonymisation of a staff actor), the system SHALL in the same statement mark every protocol version of the affected appeals `PURGE_PENDING`, which makes it unreadable at once. Purged versions' files MUST be deleted with the evidence reason `ERASURE`, leaving only an audit entry without content.

#### Scenario: Message redacted
- **WHEN** an admin redacts a message that is in protocol versions 1 and 2
- **THEN** both are unreadable immediately and their files are deleted

### Requirement: Redaction regenerates the protocol
After old versions were marked, the system MUST generate a new version in which redacted entries appear as markers and erased authors as anonymous. A failure of the regeneration MUST NOT undo the redaction and is retried by the reconciler.

#### Scenario: Participant erased
- **WHEN** an admin erases the Discord participant
- **THEN** the new version shows an anonymous author and no earlier version remains readable

#### Scenario: Regeneration fails
- **WHEN** the new version cannot be stored after a redaction
- **THEN** the old versions stay unreadable and the reconciler stores the new one later

### Requirement: Protocol events carry no content
The system SHALL publish `case.protocol_stored` (appeal id, version, evidence id, entry count) without content, after the write and without failing it, and the portal allow-list MUST NOT include `protocol.stored`.

#### Scenario: Event
- **WHEN** a protocol is stored
- **THEN** the published event holds identifiers and counts only

#### Scenario: Player timeline
- **WHEN** the player reads the conversation in the portal
- **THEN** no `protocol.stored` entry is returned
