# Punishment evidence

`evidence/` holds anticheat records, chat excerpts, links and uploaded files attached to
punishments. Detail of the decisions: `openspec/changes/archive/2026-10-23-add-punishment-evidence/design.md`.

- **Lifetime = punishment record.** There is deliberately no time-based expiry and no retention
  sweep for evidence. It is deleted only with its punishment (`deleteForPunishment`, reason
  `CASCADE`) or by an admin (`DELETE /evidence`, reason mandatory, audited). Do not add expiry, and
  never use S3 lifecycle rules. `EvidenceHousekeepingSweeper` removes only unclaimed pending items
  (`pending-ttl`), files without a row (older than one day) and, if configured, old audit rows.
- **Status, not deletion.** A staff revoke marks items `REVOKED`, a granted full-lift appeal marks them
  `LIFTED` (via `PunishmentEvidenceGateway`, failures logged, never failing the punishment change).
  Inactive items are hidden and not counted unless `includeInactive=true`, which is audited. That
  hiding is advisory: every role that may read evidence (VIEWER and up) can reveal it, and each reveal is audited.
- **`PunishmentEvidenceGateway` is the only door** the punishment and appeal packages use; they must
  not depend on `EvidenceService` or the blob store directly. Punishment/appeal DTOs expose only
  `evidenceCount`, which is null in cached profile listings.
- **GDPR.** Owners are 128-hex hashes; payloads reject UUID/IP-looking strings (`PiiGuard`), chat IPs
  are redacted, audit entries and events carry no content. Never log or publish payloads or file names.
- **Uploads fail closed.** `UploadPipeline` scans first (flagged -> 422, scanner down -> 503), then
  sniffs magic bytes (the client MIME type is ignored), enforces caps and re-encodes images. Video
  metadata is not stripped. Keys are server generated; the filesystem store guards against traversal.
- **Storage** sits behind `BlobStore` (`S3BlobStore` default, `FilesystemBlobStore`). Tests use
  `InMemoryBlobStore`, a fixed `TestClock` and `EvidenceTestBed`; no sleeps, no real network in unit tests.
- Config is `blackhole.evidence.*` (`EvidenceConfig`, created eagerly so a bad value fails startup);
  document every new tunable next to its default in `application.yml`.

## Transcript evidence (the appeal protocol)

Detail: `openspec/changes/add-appeal-portal/specs/punishment-evidence/spec.md` and design decision 16. Kind `TRANSCRIPT`
(ordinal 5, `V17`) is generated by the backend only; `EvidenceService.attach` and `PayloadValidator` answer 400 and the upload
route only makes `FILE`.

- **A file pair.** `file_key` holds the text, `json_file_key` (+ size, sha256) the JSON; `payload` holds ids and counts
  (`appealId`, `version`, `entries`, `digest`), never content. `EvidenceService.deleteForPunishment`, `remove` and the orphan
  sweep (`existsByJsonFileKey`) know the second key.
- **`GeneratedEvidenceGateway`** (`GeneratedEvidenceService`) is the only door the protocol uses: `store` (no sniffing,
  scan, re-encoding or UUID/IP guards, so the record stays as it is; each file at most `blackhole.protocol.max-bytes`,
  default 16 MiB, otherwise `StoreException.tooLarge()` and nothing stored), `open` (audited `VIEWED`/`DOWNLOADED`) and
  `delete` (reason `ERASURE` for purges, `DUPLICATE` for a run that lost the version race).
- **Never marked, never counted.** `changeStatus` skips `TRANSCRIPT` (a lifted or revoked punishment keeps its protocol
  `VALID`), `countValid` excludes it (`countByPunishmentIdentifierAndStatusAndKindNotEqual`), listings return it.
- **Unreadable after a redaction.** `EvidenceService.get` and `content` ask `TranscriptAccess.readable` (implemented by
  `JdbcProtocolStore`); a version marked `PURGE_PENDING` or `PURGED`, or without an index row, answers 404.
- `CaseReconciler` skips `TRANSCRIPT` (`protocol.stored` is its timeline event, not `evidence.attached`).

- Discord channel files: only the bound player's and verified staff's files are evidence, uploaded with `POST /discord/tickets/{id}/attachments`
  (the `CHAT` profile, bound to the case at once, id derived from ticket and Discord attachment id, provenance `PLAYER` or `STAFF`). Every other
  Discord attachment stays metadata only (name, type, size; `rejected` code when refused) and the Discord id is never stored. The bot fetches
  accepted files back with `GET /discord/tickets/{id}/attachments/{attachmentId}` (same visibility as the player route, scoped to the case).
  The ticket's protocol is still the `TRANSCRIPT` evidence of the appeal (see `case-timeline.md`); the Discord archive and delete gates depend on it.

## Chat files, provenance and sharing (appeal chat)

Detail: `openspec/changes/add-appeal-chat/` (design decisions 2 to 6; specs `appeal-chat`, `punishment-evidence`, `evidence-sharing`), migration `V23__chat_attachments_and_shares.sql`.

- **Provenance.** `evidence_items.provenance` (`EvidenceProvenance`: `STAFF` 0, `PLAYER` 1, append-only ordinal, default `STAFF`, so every old row is staff
  evidence). Evidence responses carry it; the panel labels `PLAYER` items "player-supplied, unverified". **`countValid` (and so every
  `evidenceCount`, the public punishment and `GET /punishment/{ref}/evidence/count`) counts `STAFF` items only**, so a banned player cannot change the
  number on their own ban screen; `countPlayerSupplied` and `CountResponse.playerSupplied` are the separate figure. Never fold them together.
- **Upload profiles.** `UploadPipeline.process(file, name, UploadProfile)`: `EVIDENCE` is the old behaviour (PNG, JPEG, MP4, WebM; WebP/PDF/text are 415 even
  if configured), `CHAT` is PNG/JPEG (re-encoded), WebP (`WebpSanitizer`: RIFF of exact length, EXIF/XMP chunks dropped, animation 415, trailing bytes 422,
  pixel cap from the canvas header, never decoded), PDF (`PdfGuard`: `%PDF-` in the first KiB, names such as `/JavaScript`, `/OpenAction`, `/Encrypt`
  read with `#xx` escapes -> `FILE_ACTIVE_CONTENT`), UTF-8 text (`TextGuard`: strict, no NUL/control, not `<svg`/`<html`/`<?xml`/`<script`, tried last).
  Scan first, then sniff, then caps; a flagged chat file is `FILE_FLAGGED` (422, **no signature name**), a down scanner 503. `FileNames.sanitizeChat` turns a
  name with a UUID, IP or `#` + 8 Ban ID shape into `attachment.<ext>`. Config `blackhole.chat.attachments.*` (`ChatAttachmentConfig`): sizes, counts, quota.
- **Staged, then bound.** `ChatFileService.stage` stores a pending item (`punishment_identifier` NULL, `correlation_id` `chat:<scope>`: the appeal id for a
  player, the punishment id for staff, `ChatFiles.appealScope|caseScope`). Staged items are in no listing, count, owner listing, `GET /evidence/{id}` or
  `/content` (`isStagedChatFile`). The message binds them inside `CaseChanges.appendMessage(draft, promote, Claim)` (one CTE, `FOR UPDATE`, all or
  nothing, idempotent with the dedupe key); a bound file **keeps its `chat:` correlation id** so `countByCorrelationId` is the per-appeal quota
  (`QUOTA` 409: `max-staged`, `max-files-per-appeal`). `ChatFiles` is the narrow door the case package uses; `EvidenceService`'s sweep removes unbound
  items after `pending-ttl` like any pending item.
- **Erasure.** Redacting a message and the player-side erase delete the files and blobs **before** they redact (`ChatFiles.deleteFiles|deletePlayerFiles`,
  reason `ERASURE`); a blob that cannot be deleted answers 503 and redacts nothing, so a retry finishes the job. The cascade with the punishment is unchanged.
- **Sharing** (`evidence/share/`). Evidence is never visible to a player without an active `evidence_share` row (one per appeal, item and selection; unique
  partial index while not revoked). Only a `CHAT_LOG` (EXCERPT) or a **team** image file (FILE) is shareable; everything else, video, PDF/text and a player's
  own file is 422 `NOT_SHAREABLE`. An excerpt stores line indexes (sorted, at most `blackhole.chat.share.max-lines`, default 20) and the appellant speaker;
  `ExcerptRenderer` renders on read ("You", "Player 2", ..., times as offsets, plain text), so there is no second copy and a deleted item reads
  `UNAVAILABLE`. `confirmedMinimised: true` is enforced by the backend (400 `NOT_CONFIRMED`), the confirming `oid` is `shared_by_oid`; each selected line
  passes `PiiGuard` again (422 `PII_REJECTED`, the index only). Needs an appeal (409 `NO_APPEAL`) and a Ban ID that is not leaked (409 `FROZEN`).
  Share and revoke are one CTE each (`JdbcEvidenceShareStore`) and the case events `evidence.shared|share_revoked` (visibility `PLAYER`, dedupe per share,
  payload ids/kind/mode/line count/reason code, **no content**). `evidence_id` has no foreign key on purpose.
